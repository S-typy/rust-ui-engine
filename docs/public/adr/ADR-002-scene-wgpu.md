# ADR-002: независимая Scene и GPU backend на wgpu

Дата: 2026-10-09. Статус: принято для M0.

## Контекст

Модель интерфейса должна тестироваться без окна и GPU. Renderer должен рисовать
эту модель через нативный GPU API и сообщать причину отказа, если подходящий
адаптер недоступен. M0 проверяет простой рабочий путь от сцены до кадра;
сложная векторная графика и GPU text требуют отдельных реализаций.

## Решение и границы

В workspace остаются три пакета:

| Пакет | Ответственность |
|---|---|
| `rust-desktop-ui-core` | `Rect`, `Color`, `SolidRect`, `Scene`; геометрия без платформенных зависимостей |
| `rust-desktop-ui-render-wgpu` | Window/surface integration, adapter/device/queue, WGSL и GPU buffers |
| `gpu-shell` | `winit` event loop, демонстрационное состояние, перевод ввода и обработка ошибок |

`Scene` — список заполненных прямоугольников в логических пикселях. Порядок
добавления задаёт порядок рисования. Renderer читает сцену, применяет scale
factor на границе с физическими пикселями и отправляет экземпляры прямоугольников
в GPU buffer. Сцена не содержит `wgpu` handles и не владеет окном.

Наличие `winit` в начальном renderer допустимо: сейчас этот пакет совмещает
surface adapter и GPU backend. Выделение платформенного адаптера откладывается
до появления нескольких потребителей. Это не разрешает переносить `Window`,
`Device` или платформенные события в публичный API ядра и controls.

Сохраняются точные версии `wgpu = 30.0.1` и `winit = 0.30.13`. `Cargo.lock`
фиксирует разрешённое дерево зависимостей, Rust 1.96.0 — проверяемый toolchain.
У wgpu включены нативные D3D12, Metal и Vulkan и WGSL; GLES и WebGPU не включены.
У winit включены `rwh_06`, X11, Wayland и динамическая загрузка Wayland.
Готовые Adwaita decorations отключены. Собственной Wayland client-side рамки в
M0 нет: compositor без server-side decorations может показать окно без рамки.

## Жизненный цикл

Окно создаётся в `ApplicationHandler::resumed`. Renderer получает `Arc<Window>`,
что связывает срок жизни surface с её нативным окном. UI state и renderer
используются из event loop; отдельный render thread пока не вводится.

Renderer запрашивает совместимый с surface адаптер с предпочтением hardware
high-performance GPU. Принудительный software fallback выключен; CPU и Noop
адаптеры отвергаются. Типы Other и VirtualGpu сами по себе не доказывают
аппаратную реализацию; для оценки запуска сохраняется фактическая диагностика
adapter и backend. `WGPU_BACKEND`
позволяет ограничить выбор одним из включённых backend для воспроизводимой
проверки. Наличие драйвера и подходящего GPU проверяется при запуске.

Resize сохраняет физический размер, а настройка surface выполняется перед
следующим кадром ненулевого размера. Размер проверяется относительно GPU
limits. Нулевой viewport пропускается. Результат рисования отличает показанный
кадр, временный пропуск и необходимость восстановления; ошибка не маскируется
под успешно показанный кадр.

Timeout и occlusion пропускают кадр. Outdated приводит к повторной настройке
surface. Suboptimal frame показывается, а повторная настройка откладывается
до освобождения полученной texture. При surface/device loss shell может
пересоздать renderer до трёх раз подряд без успешно показанного кадра, после
чего возвращает содержательную ошибку. Успешный кадр сбрасывает счётчик.
Callback потери device и ошибки backend
передаются в тот же путь диагностики. Пересоздание GPU не меняет состояние
демонстрации; полноценных asset caches, которые нужно восстанавливать, пока нет.
Перед present вызывается `Window::pre_present_notify` для интеграции с
платформенной синхронизацией кадров, включая Wayland.

Перерисовка запрашивается при изменении состояния или окна. При простое
постоянный цикл рендеринга не требуется. Реальные platform resize, scale factor,
pointer, wheel и close проверяются отдельно от unit-тестов геометрии.

## Альтернативы и ограничения

- Прямая отрисовка из виджетов через `wgpu::Device` связывает runtime с одним
  backend и мешает проверять сцену без GPU, поэтому не используется.
- CPU renderer не является запасным режимом; отсутствие hardware GPU означает
  диагностируемый отказ запуска.
- Vello не добавляется как обязательная зависимость M0. Сложные пути сначала
  требуют сравнительной проверки API, GPU, качества и лицензий.
- Фиксированный batch до 16 384 прямоугольников и временный instance buffer на
  CPU достаточны для прототипа. Это не подтверждённая модель производительности
  будущих компонентов.

Обзор upstream Vello на 2026-10-09 различает три реализации: `vello_cpu`
работает на CPU; `vello_gpu` обрабатывает пути на CPU, а rasterization/compositing
выполняет на GPU без требования compute shaders; первоначальный `vello`
использует compute shaders и остаётся исследовательским renderer. Проект
распространяется по Apache-2.0 OR MIT. Для будущего сравнения подходит GPU-путь,
но его совместимость с выбранным wgpu, производительность и качество в этом
workspace пока не проверены. Для M0 достаточно собственного rectangle batch.
Источник: [Vello upstream README](https://github.com/linebender/vello#readme).

M0 не реализует glyph rendering, clips, transforms, image atlas, rounded
rectangles или dirty-region rendering. Контракт Scene будет расширяться
поэтапно. Отчёты о сборке на Windows/Linux/macOS и о GPU runtime учитываются
отдельно: успешный CI build не подтверждает показ окна, ввод или восстановление
после аппаратного сбоя.

Версионные API: [wgpu 30.0.1](https://docs.rs/wgpu/30.0.1/wgpu/) и
[winit 0.30.13](https://docs.rs/winit/0.30.13/winit/).
