# Источники данных и адаптеры

`rust-desktop-ui-data` предоставляет типизированные таблицы, источники данных
и адаптеры для Rust-коллекций и SQLite. Библиотека не зависит от controls,
оконной платформы или renderer. [GridControl](grid-control.md) использует
снимок источника и виртуализирует отображение строк.

## Значения и схема

`CellValue` содержит `Null`, `Bool(bool)`, `Integer(i64)`, `Real(f64)`,
`Text(String)`, `Decimal(DecimalValue)`, `Date(DateValue)`, `Time(TimeValue)`
и `Binary(Vec<u8>)`. Числа `Real` должны быть конечными. Поле имеет единственный
тип `FieldType` и отдельный признак `nullable`; автоматическое преобразование
числа в строку или `i64` в `f64` не выполняется.

`FieldSchema` задаёт `name`, `title`, `kind`, `nullable`, `read_only`.
`TableSchema::new` проверяет уникальность и размер имён. `DataRow` содержит
устойчивый ключ `i64` и значения в порядке схемы. `DataTable::new` проверяет
все строки, типы, уникальность ключей и ограничения объёма до публикации.

Ключ строки не зависит от позиции после сортировки и фильтрации. Поддерживается
весь диапазон `i64`, включая отрицательные значения. Привязка выбранного ключа
GridControl передаёт десятичную строку или `null`, сохраняя точность значений,
которые невозможно точно представить в `DataValue::Number(f64)`.

`DecimalValue::new(coefficient, scale)` хранит знаковый коэффициент `i128`
и от 0 до 28 десятичных разрядов после точки. Конструктор и `FromStr` проверяют
диапазон; переполнение и лишние разряды отклоняются, округления нет.
Незначащие дробные нули нормализуются: `1.2300` равно `1.23`, `-0.00` равно `0`.
Значение не проходит через `f64`. Сортировка сравнивает десятичные величины
без умножения, способного переполниться. Экспоненциальная запись не принимается.
Это тип значения; арифметика и валютное форматирование не входят в его контракт.

`DateValue` — григорианская дата от `0001-01-01` до `9999-12-31`, включая
проверку високосных лет. `TimeValue` — время суток `00:00:00`–`23:59:59.999999999`
с наносекундной точностью. Часовые пояса и leap seconds не подразумеваются;
недопустимые компоненты отклоняются. Поля этих типов закрыты и создаются
проверяемыми конструкторами или парсерами. `Display`/`FromStr` у даты используют
ISO `YYYY-MM-DD`; время принимает `HH:MM`, `HH:MM:SS` и дробные секунды до
девяти разрядов. Канонический `Display` времени всегда содержит секунды.

`FieldSchema::parse` разбирает текст редактора. Числа используют точку для
дробной части; bool принимает `true/false`, `1/0`, `да/нет` без учёта регистра.
Дата редактора имеет формат `ДД.ММ.ГГГГ`, время — `ЧЧ:ММ` с необязательными
секундами и дробной частью. `CellValue::display` не отбрасывает ненулевые
секунды или наносекунды. Binary разбирается как `0x` и пары шестнадцатеричных
цифр: `0x00FF`, пустой массив — `0x`. Регистр цифр при вводе не важен.
Пустое значение любого nullable-поля, кроме текста, означает `Null`.
Текст сохраняется буквально, включая пробелы и пустую строку; для SQL NULL
текстового поля используется явный `CellValue::Null` через Rust API.
`CellValue::display` показывает bool как «Да»/«Нет», null — пустой строкой.
Пустые текст, binary и null различаются как значения.

## Rust-коллекция

```rust
use rust_desktop_ui_data::{
    CellValue, CollectionAdapter, DataError, DataRow, DataSource, DataTable,
    FieldSchema, FieldType, TableSchema,
};

fn products() -> Result<DataSource, DataError> {
    let schema = TableSchema::new(vec![
        FieldSchema::new("Name", FieldType::Text),
        FieldSchema::new("Quantity", FieldType::Integer),
    ])?;
    let table = DataTable::new(schema.clone(), vec![
        DataRow::new(101, vec![
            CellValue::Text("Клавиатура".into()), CellValue::Integer(12),
        ]),
    ])?;
    let adapter = CollectionAdapter::new(table);
    let collection = adapter.handle();
    let mut source = DataSource::new(adapter)?;

    source.set_cell(101, "Quantity", CellValue::Integer(14))?;

    // Внешняя замена коллекции: схема и исходные limits сохраняются.
    collection.replace(DataTable::new(schema, vec![
        DataRow::new(101, vec![
            CellValue::Text("Клавиатура".into()), CellValue::Integer(18),
        ]),
        DataRow::new(102, vec![
            CellValue::Text("Мышь".into()), CellValue::Integer(25),
        ]),
    ])?)?;
    source.synchronize()?;
    Ok(source)
}
```

`CollectionHandle` — совместимое имя `ObservableCollection`. Handle можно
клонировать; `snapshot()` возвращает принятую таблицу, `replace()` атомарно
заменяет её. Доступны также вставка, удаление, перемещение, изменения полей
и атомарные пакеты. Источник принимает уведомления через `synchronize()`;
GridControl вызывает его при update. Запись ячейки через источник публикует
изменение в той же коллекции. Уведомления и подписки не перехватывают изменения
произвольного `Vec`. Подробности — [наблюдаемые коллекции](observable-collections.md).

`replace_schema(schema, rows)` явно заменяет схему и все строки наблюдаемой
коллекции. Все значения уже должны соответствовать новой схеме; преобразований,
добавления null или отбрасывания колонок по предположению не происходит.
Проверка использует прежние ограничения получателя. Успех публикует одну ревизию
и `Reset`, ошибка сохраняет схему, строки, ревизию и журнал. Обычный `replace()`
по-прежнему требует неизменную схему. Поля `read_only` защищают пользовательские
изменения ячейки; приложение может заполнять их при замене строки или схемы.

## SQLite

Адаптер доступен с feature `sqlite`. Workspace закрепляет `rusqlite` и
собирает bundled SQLite из C-исходников; установка SQLite DLL не требуется.
`SqliteConnection` экспортирует тип соединения для подготовки схемы приложением.

```rust,no_run
use rust_desktop_ui_data::{
    DataError, DataSource, FieldSchema, FieldType, SqliteAdapter,
    SqliteTableConfig, TableSchema,
};

fn open_products() -> Result<DataSource, DataError> {
    let schema = TableSchema::new(vec![
        FieldSchema::new("Name", FieldType::Text),
        FieldSchema::new("Quantity", FieldType::Integer),
    ])?;
    let config = SqliteTableConfig::new("Products", "Id", schema)?;
    DataSource::new(SqliteAdapter::open("products.db", config)?)
}
```

`open()` открывает существующий файл для чтения/записи и не создаёт отсутствующую
БД. `from_connection()` принимает готовое соединение, в том числе in-memory.
Создание таблиц, миграции и выбор файла принадлежат приложению. `with_limits()`
позволяет уменьшить допустимый размер snapshot. Ожидание блокировки — 250 мс;
его истечение возвращает ошибку, сохраняя принятый снимок.

Конфигурация выбирает одну таблицу, колонку устойчивого ключа и поля схемы.
Ключ обязан содержать уникальные непустые SQLite INTEGER. Если ключ также
включён в видимые поля, он должен быть `read_only`, `Integer`, `nullable=false`.
Отображение типов хранилища строгое:

| FieldType | SQLite storage class и представление |
|---|---|
| Integer | INTEGER, весь диапазон `i64` |
| Bool | INTEGER, только 0 или 1 |
| Real | REAL, только конечное значение |
| Text | TEXT, корректный UTF-8 |
| Decimal | TEXT, канонический `DecimalValue::to_string()` |
| Date | TEXT, `YYYY-MM-DD` |
| Time | TEXT, `HH:MM:SS` и при необходимости дробные секунды без конечных нулей |
| Binary | BLOB, включая пустой массив |
| nullable | NULL независимо от типа поля |

Для Decimal/Date/Time приложение объявляет колонки с TEXT affinity, для Binary —
BLOB. Например, decimal `1.23` хранится как `'1.23'`, а не `'1.2300'` или REAL;
время `12:30` хранится как `'12:30:00'`. Неканонический текст отклоняется,
сохраняя однозначность проверки ожидаемого значения. Неподходящая NUMERIC
affinity, округляющая decimal при записи, приводит к rollback. Никакой DDL
адаптер не выполняет. Несовместимые динамические типы отклоняются.
Идентификаторы экранируются, значения
передаются параметрами; SQL-выражения из фильтра или XAML не исполняются.

Изменение ячейки использует immediate transaction и проверяет прежнее значение.
Изменённая или удалённая другим соединением строка вызывает conflict.
Ограничение БД, несовместимое преобразование affinity/trigger, превышение лимитов
обновлённого snapshot или ошибка commit откатывают операцию. Новый снимок
считывается и проверяется внутри транзакции до commit. При ошибке источник
сохраняет старую таблицу и revision; редактор может сохранить свой черновик.

## Источник, запросы и ошибки

`DataSource::new(adapter)` синхронно загружает первый снимок либо возвращает
ошибку. Далее `table()` предоставляет исходные строки, а `row_key(index)`,
`position(key)` и `len()` — текущий отфильтрованный порядок. `row(key)` и
`value(key, field)` доступны также для записей, скрытых фильтром. Чтение этих
свойств не обращается к адаптеру. У каждого экземпляра источника свой query.

`DataQuery` содержит `sort: Vec<SortDescriptor>` и `filter: String`.
Сортировка выполняется по типизированным значениям, а не их текстовому виду.
Null идёт первым по возрастанию и последним по убыванию. Направление каждого
поля независимо; при равенстве всех полей используется ключ по возрастанию.
Текст сортируется регистрозависимо по обычному порядку Rust strings, без
локализованной collation; Binary — лексикографически по беззнаковым байтам.
Decimal сравнивается численно, Date и Time — хронологически. При пустом sort сохраняется порядок снимка:
порядок переданной Rust-коллекции или ключи SQLite по возрастанию.

Фильтр ищет подстроку в отображаемых значениях всех полей, применяя Unicode
lowercase к строке поиска и значениям. Это не регулярное выражение и не
локализованный поиск. Сортировка и фильтрация одинаковы для обоих адаптеров,
выполняются локально после загрузки и никогда не запускают SQL при paint.

Для составных условий, вычисляемых выражений, группировки и итогов используется
отдельный [Query Engine](query.md): `QueryRequest`, `Criteria`, `QueryExpression`
и `QueryEngine`. `DataSource::evaluate_query(&request)` читает полный принятый
snapshot, не меняя текущий `DataQuery`, revision и состояние редактора.
`QueryEngine::execute_provider` — явная операция чтения адаптера с проверяемым
контрактом capabilities; встроенные коллекции и SQLite используют общий локальный
движок. Наличие SQL-хранилища само по себе не означает поддержку pushdown.

`refresh`, `set_query`, `set_cell` и `set_cell_expected` возвращают `bool`:
принято ли изменение. Успешный no-op не повышает revision. Последняя ошибка
доступна через `last_error()`; следующая успешная операция её очищает.
Исключение — `synchronize()` без новых уведомлений: он не загружает данные
и сохраняет прежнюю ошибку до следующего реального обновления или явной операции.
Неудачная операция сохраняет снимок, query, видимый порядок и revision.
`set_cell_expected` проверяет принятое значение конкретной ячейки, поэтому
изменение другого поля само по себе не создаёт conflict.

`refresh()` и `synchronize()` могут принять новую схему адаптера, если текущий
query остаётся допустимым. Смена схемы, включая только заголовки или read-only,
даёт `Reset`. Если сортируемое поле удалено, принятие завершается ошибкой
и сохраняет последнюю пригодную таблицу. `refresh_with_query(new_query)` позволяет
одной операцией загрузить новую схему и заменить query; ошибка любого шага
не меняет принятое состояние. Перед записью черновика ещё не принятую смену
схемы источник отклоняет с `Conflict`: сначала требуется обновить представление.

`replace_adapter(new_adapter, query)` заменяет живой источник после успешной
проверки первого снимка и query. Так приложение может подготовить SQLite DDL
и новый `SqliteTableConfig`, а затем подключить новую схему. Ошибка нового
адаптера оставляет прежний адаптер работающим. Метод не мигрирует данные и
не откатывает внешние действия приложения. Изменённый снимок получает `Reset`;
при идентичном снимке и query подключение меняется без новой ревизии.

`subscribe_notifications(Box<dyn Fn(u64)>)` возвращает владеющий токен подписки
источника. Подписка переживает `replace_adapter`: мост к новому адаптеру
регистрируется до принятия замены, старый снимается при успехе. Внутренний мост
держит слабую ссылку, а уничтожение источника деактивирует подписки.
Callback служит только для постановки обновления в очередь: он может вызываться
во время изменяющего метода источника, поэтому не должен повторно заимствовать
этот источник. Переданное число — подсказка для пробуждения, не cursor журнала
`DataSource`; после пробуждения читаются `revision()`/`changes_since()`.
Вложенные wake hints объединяются с текущей доставкой: callback обязан
запланировать последующее обновление, которое увидит все принятые изменения.
Для SQLite внешние изменения по-прежнему требуют явного `refresh()`.

Если подписчик коллекции меняет данные или схему во время записи, адаптер
возвращает снимок и cursor именно принятой записи, сохранённые до callback.
Последующее изменение подписчика остаётся ожидающим следующего `synchronize()`.
Оно не превращает успешно принятую запись в ошибку и не теряется из-за
слишком нового notification cursor.

`DataAdapter` можно реализовать самостоятельно. `load()` возвращает полностью
проверенный `DataTable`; `write_cell()` должен атомарно изменить backing store
и вернуть итоговый снимок либо не менять хранилище при ошибке. Схема может
меняться через полный результат `load()`, но не в ходе `write_cell()`.
Limits остаются постоянными на протяжении жизни адаптера; их явная смена
возможна при `replace_adapter`. UI-поток и worker выбирает
приложение; библиотека не создаёт потоков или фоновых соединений.

## Ограничения текущего профиля

| Ограничение | По умолчанию и максимальное значение |
|---|---:|
| Строки | 100 000 |
| Поля | 128 |
| UTF-8 текст одной ячейки | 1 МиБ |
| Binary одной ячейки | 1 МиБ |
| Расчётный объём таблицы | 64 МиБ |
| Имя поля | 256 UTF-8 байт |
| Заголовок / filter | 4096 UTF-8 байт |

`DataLimits` разрешает уменьшать границы. Объём учитывает строки, ключи, ячейки,
текст, binary payload и индексы, но не является точным измерением allocator overhead; временные
копии при проверке и публикации также занимают память. SQLite проверяет лимиты
во время чтения и запрашивает максимум `max_rows + 1`, чтобы обнаружить
превышение без молчаливого усечения.

Снимок загружается целиком; виртуализация GridControl сокращает UI-работу,
но не объём загруженных данных. Server mode, SQL paging/sort/filter, async
loading, ORM, SQL joins, специализированные blob-редакторы и готовые HTTP/JSON/CSV
адаптеры не входят в этот профиль. Для больших или медленных источников требуется
отдельный контракт фоновых запросов и постраничного доступа.
