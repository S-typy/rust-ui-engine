# Дизайнер отчётов и Dashboard

Компоненты монтируются через Rust API в существующий `Controls`. Отдельных
compiled XAML тегов для этих компонентов пока нет. Пример `xaml-form` использует
обычную XAML-форму с контейнером для выбранного компонента:

```text
cargo run -p xaml-form -- --report-designer
cargo run -p xaml-form -- --dashboard
```

`--composition-preview` открывает предпросмотр отчёта либо режим редактирования
Dashboard. `--light` и `--dark` выбирают оформление.

## Дизайнер отчётов

`ReportDesignerSession` владеет принятой `ReportDefinition`, снимком `DataTable`,
значениями параметров, выделением и историей. `ReportBandKind` адресует семь
секций: заголовки и окончания отчёта, страницы и группы, а также detail.
`ReportSelection` содержит секцию и индекс элемента в текущей версии.

`add`, `replace_selected`, `delete_selected`, `move_selected` и `replace`
проверяют целый кандидат через `ReportEngine` до публикации. Неверные координаты,
типы, ссылки на поля и параметры сохраняют прежние definition, preview и history.
`replace`/`restore` требуют актуальный `ReportRevision`: отложенный ответ не
перезаписывает более новое редактирование. Undo/redo обновляют revision; устаревший
токен не становится актуальным после возврата к прежнему содержимому.

Предпросмотр всегда соответствует принятому документу и данным. Изменения текста
в панели свойств остаются черновиком до команды «Применить». Resize не заменяет
редакторы. Смена выделения загружает свойства другого элемента, поэтому незавершённый
черновик свойств следует сначала применить или отменить.

`ReportDesigner` предоставляет поверхность секций, координатные направляющие,
выбор и перенос элемента, toolbox текста/прямоугольника/изображения, свойства,
undo/redo и просмотр страниц. Стрелки перемещают выделение с шагом 8 DIP;
Ctrl уменьшает шаг до 1 DIP. Shift со стрелками или переносом изменяет размер.
Для текста вертикальное изменение размера регулирует шрифт.
`move_selected` дополнительно поддерживает явное округление позиции к сетке.
Текст свойства с `=` задаёт выражение общего query-языка, с `@` — параметр.
Специальные вычисляемые значения, например номер страницы, сохраняются как
`ReportValue`; их конфигурация доступна через Rust API.

`ReportDefinition::to_json/from_json` сохраняют определение, а не готовые страницы.
Формат версии 1 строгий: неизвестные поля, виды элементов и версии отклоняются.
Ошибочный restore не заменяет текущий документ. Декодирование требует схему
данных; окончательную проверку геометрии/значений выполняет session или engine.
Максимум — 4 MiB JSON, 512 KiB RGBA на встроенное изображение. Действуют также
ограничения [движка отчётов](printing-and-reports.md). История содержит до 64
снимков и до 16 MiB сериализованных определений.

`set_data` сначала проверяет новый снимок и параметры. При успехе он очищает
историю, поскольку прежние привязки могут отсутствовать в новой схеме.
Модель выполняет вычисления синхронно; для больших отчётов приложение должно
организовать работу с моделью на своём worker и проверять revision результата.
Пример использует небольшой набор данных, явные Open/Save JSON и экспорт PDF.
Чтение, запись и PDF encoding выполняются на рабочем потоке.

## Dashboard

`DashboardDefinition` описывает название, число колонок, элементы и параметры.
`DashboardItem` имеет стабильный строковый ID, источник, `QueryRequest`,
`DashboardPlacement` и вид `DashboardWidget`:

| Вид | Представление |
| --- | --- |
| `Grid` | Существующий read-only `GridControl` |
| `Chart { x, y }` | Существующая диаграмма над числовыми полями |
| `Metric { aggregate }` | Один итог общего Query Engine |
| `Missing { name, payload }` | Диагностика недоступного виджета с сохранением payload |

Viewer и designer используют одно определение. `Dashboard` сохраняет WidgetId
таблиц и диаграмм при изменениях фильтров/данных; изменение состава или расположения
создаёт новую композицию. Заголовок выбирает элемент для изменения названия,
перестановки либо удаления. Можно добавить таблицу, отменить и повторить правку.
Виды виджетов, запросы, параметры и произвольная компоновка настраиваются через
Rust API или JSON. Контейнер прокручивается, сохраняя минимальную высоту плиток.

`DashboardSession` принимает `DashboardSources`, именованные неизменяемые
`DataTable`. Приложение получает их от адаптеров/`DataSource`; отрисовка не
вызывает I/O. `refresh_sources` и `restore` проверяют revision и весь кандидат.
Смена источников очищает историю определений.

`set_filter(revision, origin, filter)` — явное событие выбора пользователя:

- Значения проверяются по типу поля, без преобразования через display string.
- Фильтр передаётся другим элементам того же источника. На отправителя его
  собственный фильтр не действует; остальные фильтры и параметры действуют.
- Фильтры разных отправителей объединяются через AND, значения одного — OR.
  Пустой список значений выбирает ноль строк; `None` снимает фильтр.
- Повторная передача того же фильтра не меняет revision.
- Перерисовка и обновление данных не порождают новые события фильтрации.

В стандартном представлении строка Grid фильтрует по первому полю, точка Chart —
по X. Для иной связи приложение вызывает `set_filter` с нужным полем.
Выбор, временные фильтры и подключённые источники не включаются в JSON. Значения
именованных параметров входят в определение.

Лимиты: 32 элемента, 32 источника по 20 000 строк, 32 параметра, 128 значений в
одном фильтре, 12 колонок/64 строки компоновки, 1 MiB JSON и 64 KiB payload
недоступного виджета. Пересечения плиток и повторные ID отклоняются. История —
64 определения/8 MiB. Ограничения диаграмм и таблиц сохраняются; например,
диаграмма не принимает больше собственного лимита точек.

Полноценный нативный accessibility-профиль поверхности дизайнера, подтверждение
его ввода/IME и общий Grid/Table provider требуют отдельных оконных проверок.
Canvas не объявляется доступной структурой всех элементов только по наличию имени.
Визуальная компоновка, данные и сериализация проверяются отдельно от этих сценариев.
