# Наблюдаемые коллекции

`ObservableCollection` в `ui-data` хранит типизированные `DataRow` со стабильными
ключами `i64`. Она сообщает об изменениях состава и полей, поддерживает атомарные
пакеты и может одновременно питать GridControl, ListBox, ComboBox и LookupEdit.
Для собственных Rust-структур без табличной схемы служит `ObservableList<T>`.
Оба вида коллекций изменяются через явные методы и поддерживают подписки,
независимые курсоры и ограниченный журнал.

## Изменения

```rust
use rust_desktop_ui_data::{
    CellValue, CollectionAdapter, CollectionMutation, DataSource,
    DataTable, ObservableCollection,
};

fn observe(table: DataTable) -> Result<(), rust_desktop_ui_data::DataError> {
    let rows = ObservableCollection::new(table);
    let mut source = DataSource::new(CollectionAdapter::from_collection(rows.clone()))?;
    // Строка 101 должна существовать, а поля соответствовать схеме таблицы.
    rows.batch(vec![
        CollectionMutation::UpdateCell {
            key: 101, field: "Name".into(), value: CellValue::Text("Монитор".into()),
        },
        CollectionMutation::UpdateCell {
            key: 101, field: "Quantity".into(), value: CellValue::Integer(8),
        },
    ])?;
    source.synchronize()?; // GridControl вызывает это при обычном update.
    Ok(())
}
```

| Метод | Действие |
|---|---|
| `add(row)`, `insert(index, row)` | Добавить запись с уникальным ключом |
| `remove(key)` | Удалить запись |
| `move_row(key, index)` | Переместить запись; индекс задаёт итоговую позицию |
| `replace_row(key, row)` | Заменить запись с сохранением её ключа |
| `update_cell(key, field, value)` | Изменить одно поле |
| `update_cell_expected(...)` | Изменить поле при совпадении исходного значения |
| `clear()`, `reset(rows)`, `replace(table)` | Очистить или заменить содержимое |
| `replace_schema(schema, rows)` | Атомарно заменить схему и данные |
| `batch(mutations)` | Проверить и опубликовать пакет одной ревизией |

Обычные операции сохраняют схему; `replace_schema` проверяет новую схему и все
строки, затем публикует `Reset`. Исходные `DataLimits` сохраняются при любой
замене. Неудачный пакет не публикует частичных
изменений. Пакет с итоговым содержимым, равным исходному, не повышает revision.
Ключ не зависит от позиции; удалённый ключ не следует повторно использовать
для другой логической записи, пока существуют её ссылки или черновики.
`CollectionHandle` сохраняется как совместимое имя наблюдаемой коллекции.

## Уведомления и жизненный цикл

Каждый наблюдатель хранит свой revision и читает `changes_since(revision)`.
Изменения описываются как Add, Remove, Move, Replace, Cell и Reset; DataSource
также отмечает смену Query. Журнал содержит метаданные, а актуальные значения
читаются из принятого снимка. Он ограничен 256 публикациями и 4096 событиями;
для устаревшего курсора возвращается Reset. Один пакет содержит до 1024 операций
и до 64 МиБ входных значений; принятая таблица дополнительно ограничена её
собственными DataLimits.
Чтение журнала одним наблюдателем не удаляет уведомления остальных.

`DataSource::synchronize()` проверяет версию наблюдаемого адаптера. При отсутствии
изменений снимок повторно не загружается. Обычные адаптеры, включая SQLite,
по умолчанию требуют явного `refresh()`; синхронизация не опрашивает базу данных.
Запись GridControl через CollectionAdapter публикуется в той же коллекции,
поэтому новое значение доступно и другим представлениям.

Коллекция принадлежит потоку приложения (`Rc<RefCell<...>>`) и не является
`Send`/`Sync`. `subscribe(callback)` возвращает `CollectionSubscription`.
Токен удерживают до отключения потребителя; `unsubscribe()` или уничтожение
токена удаляет подписку. Сам токен не удерживает коллекцию. Для захвата коллекции
в её callback используйте `downgrade()` и `WeakObservableCollection::upgrade()`.

```rust
use rust_desktop_ui_data::{DataError, ObservableCollection};

fn observe_changes(rows: &ObservableCollection) -> Result<(), DataError> {
    let weak = rows.downgrade();
    let subscription = rows.subscribe(move |revision| {
        if let Some(rows) = weak.upgrade() {
            // Здесь snapshot/journal уже содержат опубликованные изменения.
            assert!(rows.revision() >= revision);
        }
    })?;
    // Храните subscription вместе с потребителем; этот пример отключает его.
    subscription.unsubscribe();
    Ok(())
}
```

Callback выполняется синхронно после принятия пакета, без заимствования состояния
коллекции или списка подписчиков. Пустые, неудачные и итогово неизменившиеся
пакеты не вызывают callback. При регистрации начального вызова нет. Аргумент —
сигнал о ревизии для обновления, а не эксклюзивный снимок этой версии: другой
подписчик мог уже изменить коллекцию. Точные изменения читаются своим курсором.
Для окна callback должен только запросить обновление через платформенный waker;
чтение проекции выполняется при следующем update. Коллекция сама не создаёт
event loop, таймер или поток и не опрашивает хранилище.

Подписчики вызываются в порядке регистрации. Новая подписка начинает получать
события со следующего прохода, удаление действует сразу, включая текущий проход.
Изменение коллекции из callback принимается сразу и планирует следующий проход
без рекурсивного вызова; несколько изменений объединяют сигнал до последней
ревизии. Журнал сохраняет все принятые изменения. Не более 1024 подписок и 1024
повторных публикаций из callback на один цикл доставки: превышающая лимит
мутация возвращает `DataError::Capacity`, сохраняя последнее принятое состояние.
Это ограничивает ошибочную обратную связь. Ошибки мутаций следует обрабатывать.
Паника callback передаётся вызывающему после доставки остальным подписчикам;
уже опубликованные данные сохраняются, следующая доставка остаётся рабочей.

Результаты фоновой работы передаются в поток приложения через его очередь.
Наблюдаемая коллекция не выдаёт изменяемых ссылок на своё содержимое.

Для окна `Controls::set_data_waker` подписывает общие источники таблиц;
подписка `DataSource` сохраняется при замене его адаптера. Для списков DataContext
используйте `BindingContext::subscribe_collection_wake` и храните возвращённый
guard вместе с представлением. Он охватывает текущие и будущие регистрации.
Копии BindingContext разделяют сигналы обновления, но сохраняют собственные
принятые значения и курсоры. Callback только планирует update, не заимствуя
источник или контекст повторно. На закрытии форма освобождает подписки.
Потокобезопасный `AppWaker` можно передать worker, а саму коллекцию — нельзя;
worker кладёт результат в очередь приложения и запрашивает update. Контракт
доставки и закрытия описан в [native host](platform.md#уведомления-и-жизненный-цикл-окна).

## Собственные структуры Rust

`ObservableList<T>` хранит устойчивый ключ `i64` отдельно от значения. Значения
требуют `PartialEq`, но не `Clone`. Снимки возвращают `ObservableItem<T>` с
`key()`, `value()` и `shared_value()`; неизменённые значения разделяются через
`Rc<T>`. Сохранённый снимок остаётся доступен после замены или удаления записи.

```rust
use rust_desktop_ui_data::{DataError, ListMutation, ObservableList};

#[derive(PartialEq)]
struct Product { name: String, quantity: i64 }

fn products() -> Result<ObservableList<Product>, DataError> {
    let products = ObservableList::new(
        vec![(101, Product { name: "Монитор".into(), quantity: 1 })],
        |product: &Product| product.name.len(),
    )?;
    products.batch(vec![ListMutation::Replace {
        key: 101, value: Product { name: "Монитор".into(), quantity: 2 },
    }])?;
    Ok(products)
}
```

Методы `add`, `insert`, `remove`, `move_item`, `replace`, `clear`, `reset` и
`batch` имеют тот же контракт атомарности и уведомлений. Изменение полей
публикуется заменой значения с сохранением ключа. `downgrade()` создаёт
`WeakObservableList<T>`; подписки используют общий `CollectionSubscription`.
Табличные представления получают явную проекцию этих значений в `DataRow` по
`TableSchema`; произвольные поля Rust-структуры автоматически не отражаются.

`ListLimits` по умолчанию ограничивает коллекцию 100 000 элементами, значение —
1 МиБ, сумму — 64 МиБ. Лимиты можно уменьшать. Переданная функция измеряет
принадлежащий значению heap payload; inline-размер `T` и метаданные элемента
учитываются дополнительно. Для скаляра функция возвращает ноль, для строки —
длину UTF-8. Она должна быть детерминированной и не изменять состояние.
Переполнение счётчиков и превышение лимитов отклоняются до публикации.

Счётчик не измеряет накладные расходы аллокатора и объём независимо удерживаемых
снимков. Внутренняя изменяемость `Cell`/`RefCell`, атомики и внешние aliases не
публикуют уведомлений: для изменения принадлежащего коллекции значения вызывайте
`replace`. Перехват произвольных операций над внешним `Vec<T>` не предусмотрен.
`PartialEq` должен выполнять обычное сравнение без побочных эффектов; изменение
коллекции во время сравнения отклоняет исходный пакет как `Conflict`.

## Привязки списков

```rust,ignore
// До монтажа формы: Products уже объявлен как DataValue::List.
context.register_collection("Products", rows.clone(), "Id")?;
```

```xml
<ComboBox ItemsSource="{Binding Products}" DisplayMemberPath="Name"
          ValueMemberPath="Id" SelectedValue="{Binding SelectedKey}"/>
```

Тот же ItemsSource работает для ListBox и LookupEdit. При регистрации каждая
строка проецируется в объект: `Id` содержит точную десятичную строку ключа,
остальные свойства соответствуют именам полей схемы. Integer также передаётся
строкой; Decimal — точной десятичной строкой, Date — ISO `YYYY-MM-DD`,
Time — `HH:MM:SS` с необходимой дробной частью, Binary — `0x` с hex-цифрами.
Эти значения имеют тип `DataValue::String`, без преобразования через f64;
Null, Bool, Real и Text сохраняют свои типы. Имя ключа не должно
конфликтовать с полем. Проекция подчиняется ограничениям BindingContext:
100 000 узлов и 4 МиБ; максимальная таблица ui-data может в неё не поместиться.

`ControlBindings::sync()` синхронизирует зарегистрированные коллекции и читает
журнал изменений модели. Привязки к неизменённым путям не перечитывают большие
списки. Изменения отдельных полей публикуют точные пути элементов. Изменение
состава, потеря истории или слишком большой набор путей обновляют проекцию
списка целиком. Состав коллекции меняется через её handle, а не через `context.set`
зарегистрированного списка или его элементов. Получить handle можно методом
`observable_collection(path)`. Выбор хранится по ключу и сохраняется при
перестановке; удаление выбранной записи очищает выбор.

Списки используют порядок самой коллекции; сортировка и фильтр DataSource
относятся к таблице и не меняют ItemsSource этих списков. `read_only` поля
запрещает изменение ячейки; принадлежащие приложению замена строки и reset
могут заполнять такие поля при загрузке данных.

## Таблица и редактирование

GridControl сам принимает изменения наблюдаемого источника при update.
При неизменном query сохраняется привязка прокрутки к верхней видимой записи.
Активный черновик не заменяется внешними данными: представление редактируемой
таблицы принимает изменения после завершения сессии. Commit проверяет исходное
значение ячейки; внешнее изменение этой ячейки или удаление строки отклоняет
запись и оставляет введённый текст. Другие представления продолжают обновляться.

Снимки и локальные query остаются ограниченными и синхронными. На изменении
типизированной таблицы возможны копирование снимка и перестроение индексов;
начальный Clear/Reset не копирует отброшенные строки, итоговый no-op не
перестраивает индекс. `ObservableList<T>` разделяет payload неизменённых
элементов между кандидатами и снимками. Структурные операции могут быть
линейными по числу элементов. Журнал изменений
не превращает источник в серверную пагинацию. Виртуализация ограничивает
число отображаемых строк, а не общий объём данных.

Пример: `cargo run -p xaml-form --release --locked -- --data`. Слева таблица
коллекции, рядом SQLite, справа три связанных списка. Команды над формой
меняют общую коллекцию; «Изменить поля» публикует два поля одним пакетом.
